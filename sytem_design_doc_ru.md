# Дизайн-документ ML-системы: Anime Score Predictor (Прогнозирование рейтинга аниме)

## 1. Цели и предпосылки

### 1.1. Зачем идти в разработку продукта?
* **Бизнес-цель:** Anime Prediction Score (APS) — это система поддержки принятия решений для производственных комитетов и студий. Она призвана облегчить процесс «зеленого света» (одобрения) идей аниме-проектов, определяя ожидаемый критический успех и рыночный отклик концепта еще до начала дорогостоящего производства.
* **В чем ценность нашего ML?** Традиционный процесс одобрения проектов зависит от множества факторов. Аниме финансируется не одной студией, а производственным комитетом (группой студий). Мы хотим, чтобы эта ML-система стала инструментом, к которому создатели аниме смогут обращаться после разработки сюжета, но до обращения в комитеты, чтобы просто загрузить проект и предсказать, стоит ли их идея реализации в принципе.

### 1.2. Бизнес-требования и ограничения
* **Единая аналитическая среда:** Система должна предоставлять инструмент симуляции сценариев «Что, если», где пользователи могут менять жанры, студии и темы, чтобы видеть колебания прогнозируемого рейтинга в реальном времени. Такой инструмент поможет скорректировать историю аниме так, чтобы она с большей вероятностью получила высокий балл.
* **Решение проблемы «холодного старта»:** Модель должна предоставлять точные прогнозы для оригинального аниме (без данных о существующих манге или ранобэ), используя тематическое картирование сходства.
* **Интерпретируемость (SHAP):** Каждый прогноз должен сопровождаться разбивкой по значимости признаков (например: «Тема "Киберпанк" сейчас в тренде, это добавляет +0.3 к вашему баллу»).
* **Ограничение:** Время вывода (инференса) не должно превышать **300 мс** для поддержки интерактивного веб-интерфейса во время мозговых штурмов.

## 2. Методология

### 2.1. Постановка задачи
Техническая задача: **Мультимодальная регрессия с учителем**. Система использует структурированные метаданные (категориальные и числовые) и неструктурированный текст (сентимент-анализ синопсиса) для прогнозирования непрерывной целевой переменной (`score`).
В настоящее время система поддерживает только числовые прогнозы, но в будущем ASP должна уметь предсказывать рейтинг на основе названия и синопсиса. Название типа «HunterXHunter», безусловно, легче запомнить и распространить, в отличие от названий вроде «Город, в котором меня нет».

### 2.2. Архитектура решения



* **Data Aggregator (Агрегатор данных):** Автоматизированные скреперы для MyAnimeList и AniList.
* **Feature Store (Хранилище признаков):** Централизованное версионирование показателей «насыщенности жанра» и «престижа студии».
* **Model Engine (Движок модели):** Ансамбль моделей XGBoost и CatBoost.
* **Observation Layer (Слой наблюдения):** Мониторинг «дрейфа концепта» (например, когда жанр типа «Исекай» начинает приносить всё меньше баллов).

### 2.3. Feature Engineering (Проектирование признаков) и предпосылки
| Сущность | Имя признака | Источник | Обработка / Проектирование |
| :--- | :--- | :--- | :--- |
| **Хайп** | `log_favorites` | MAL API | Log-нормализация для обработки аномалий (супер-хитов). |
| **Сентимент** | `synopsis_vec` | Модуль NLP | Эмбеддинги BERT для улавливания тональности (от «мрачной» до «позитивной»). |
| **Темп** | `seasonal_trend` | Внутренний | Циклическое кодирование (Sine/Cosine) месяцев выпуска. |
| **Категории** | `studio_tier` | Внутренний | Rank-encoding на основе среднего исторического балла студии. |

## 3. Разработка и валидация модели

### 3.1. Бейзлайн (Baseline) vs. Целевое решение
* **Бейзлайн (MVP):** Стандартный XGBoost, обученный на базовых метаданных (количество эпизодов, избранное, рейтинг аудитории).
* **Целевое решение (Production):** Стэкинг-ансамбль (Stacking Ensemble), сочетающий деревья решений на метаданных и слой Deep Learning для анализа текста синопсиса.

### 3.2. Стратегия валидации: Time-Series Forward Chaining
Мы избегаем стандартной $k$-fold кросс-валидации из-за риска «утечки данных» во времени. Мы используем **Forward Chaining** (последовательную валидацию):
1. Обучение на данных 2020–2025 гг. $\rightarrow$ Тест на 2026 г.
2. Обучение на данных 2020–2026 гг. $\rightarrow$ Тест на 2027 г.
Это гарантирует, что модель учится предсказывать *будущее* на основе *прошлого*.

## 4. Инференс и оптимизация

### 4.1. Производительность и аппаратное обеспечение
* **Квантование (Quantization):** Модели подвергаются прунингу и квантованию для минимизации размера `.pkl` файла при безсерверном развертывании (Streamlit/AWS Lambda).
* **Логика триггеров:** * **По расписанию:** Ежемесячное переобучение на данных о завершенных сезонных тайтлах.

### 4.2. Бизнес-правила и ограничения (Guardrails)
* **Правило 1 (Минимум жанров):** Если пользователь выбирает 0 жанров, система по умолчанию использует жанр со средним рейтингом для расчета.
* **Правило 2 (Доверительные интервалы):** Прогнозы с низкой поддержкой признаков (очень редкие комбинации жанров) должны отображать предупреждение «Высокая неопределенность».
* **Правило 3:** Система никогда не предложит «удалить» жанр для повышения балла, если этот жанр является ключевым для синопсиса (проверка через NLP).

## 5. Развертывание и мониторинг

### 5.1. Архитектура
* **Frontend:** «Pro Dashboard» на базе Streamlit.
* **Inference API:** FastAPI, контейнеризированный через Docker.

### 5.2. Мониторинг («Петля обратной связи»)
Система регистрирует «остаточную ошибку» (разницу между предсказанным и реальным баллом) для каждого аниме. Если средняя ошибка превышает 0.5 в течение 30-дневного окна, команде Data Science отправляется оповещение о «дрейфе модели» (Model Drift).
